| Почему выбрал такой масштаб | В `partsupp` 800 000 строк, в `part` 200 000, в `supplier` 10 000. Этого достаточно, чтобы размеры файлов и время записи заметно различались между форматами и кодеками, а полная загрузка и пересоздание таблиц занимают секунды. ## 2. Поднятые сервисы — и почему именно они

Стек поднят из готового примера Lakekeeper (`examples/minimal`), копия файлов лежит в `infra/`. Состояние контейнеров:

![docker compose ps -a](docs/screens/01-docker-ps.png)

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| silo (вместо MinIO) | S3-совместимое объектное хранилище, сюда физически попадают parquet-файлы (бакет `examples`) | Поддерживаемый форк MinIO с открытым кодом. Один процесс отдаёт и S3 API, и STS (временные доступы), чего Lakekeeper достаточно, чтобы выдавать движкам краткоживущие ключи без настройки IAM. Работает локально и бесплатно, в отличие от облачного S3. |
| PostgreSQL (`db`) | БД, где Lakekeeper хранит метаданные каталога | Надёжная реляционная БД с открытым кодом, поддерживается Lakekeeper «из коробки». Метаданные каталога небольшие, поэтому лёгкого одноузлового Postgres достаточно. |
| Lakekeeper | Iceberg REST Catalog: каталог метаданных таблиц | Реализует открытый стандарт Iceberg REST. Благодаря этому один и тот же набор таблиц читают разные движки (у нас Trino и StarRocks) без копирования данных. Лёгкий, запускается одной командой. |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными, читает и пишет данные в silo | Поддерживает Iceberg и умеет генерировать данные TPC-H (каталог `tpch`), поэтому ничего не нужно скачивать. Хорошо подходит для аналитических запросов и ELT на SQL. |
| StarRocks | Второй движок для части 2 (читает Bronze через тот же каталог) | Уже входит в стек примера. Читает Iceberg-таблицы напрямую через каталог Lakekeeper, быстрый для аналитических запросов. Подробности в разделе 6.2. |

### Скрипты, которыми поднимал стек

Полный `docker-compose.yaml` и параметры warehouse лежат в `infra/docker-compose.yaml` и `infra/create-default-warehouse.json`.

```bash
# Клонирование готового примера и запуск стека
git clone https://github.com/lakekeeper/lakekeeper
cd lakekeeper/examples/minimal
docker compose up -d initialwarehouse   # silo + db + lakekeeper + одноразовые сервисы настройки
docker compose up -d trino              # SQL-движок Trino (порт 9999 на хосте)
docker compose ps -a                    # проверка статусов
```

Warehouse `demo` создаётся сервисом `initialwarehouse` из `create-default-warehouse.json` (бакет `examples`, хранилище `http://silo:9000`, регион `local-01`).

В Trino каталог `lakekeeper` нужно создать вручную (в compose включено динамическое управление каталогами, `CATALOG_MANAGEMENT=dynamic`). Скрипт `sql/00_catalog.sql`:

```sql
CREATE CATALOG lakekeeper USING iceberg
WITH (
  "iceberg.catalog.type" = 'rest',
  "iceberg.rest-catalog.uri" = 'http://lakekeeper:8181/catalog',
  "iceberg.rest-catalog.warehouse" = 'demo',
  "iceberg.rest-catalog.vended-credentials-enabled" = 'true',
  "fs.native-s3.enabled" = 'true',
  "s3.endpoint" = 'http://silo:9000',
  "s3.region" = 'local-01',
  "s3.path-style-access" = 'true'
);
```

## 3. Разбор запроса — какие данные нужны

Запрос Q16 считает, сколько разных поставщиков у деталей (в разрезе бренда, типа и размера), исключая поставщиков с жалобами от клиентов.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `part` | `partkey`, `brand`, `type`, `size` | Фильтр: `brand <> 'Brand#45'`, `type NOT LIKE 'MEDIUM POLISHED%'`, `size IN (49, 14, 23, 45, 19, 3, 36, 9)`. Джойн с `partsupp` по `partkey`. Группировка и вывод `brand`, `type`, `size`. |
| `partsupp` | `partkey`, `suppkey` | Джойн с `part` по `partkey`. Агрегат: `count(DISTINCT suppkey)` даёт `supplier_cnt`. |
| `supplier` | `suppkey`, `comment` | Подзапрос: выбрать поставщиков, у которых `comment LIKE '%Customer%Complaints%'`, и исключить их из `partsupp` (`NOT IN`). |

Остальные колонки этих таблиц (`name`, `mfgr`, `container`, `retailprice`, `availqty`, `supplycost`, `address`, `phone`, `acctbal` и др.) запросу не нужны.

## 4. Медальон — решения по каждому слою

Как получены значения: число строк — `SELECT count(*)`, вес — сумма `file_size_in_bytes` из служебной таблицы `"таблица$files"` (скрипт `sql/05_stats.sql`). Формат везде Parquet. Сжатие по умолчанию в Trino для Iceberg — ZSTD, это согласуется с замером: вес `partsupp` в Bronze (27,9 МБ) совпадает с вариантом Parquet+ZSTD в бенчмарке (27,85 МБ).

### Silver (очищенный)

Скрипт `sql/02_silver.sql`. Что сделано:
- соединены `partsupp` и `part` по `partkey` (одна таблица «деталь–поставка»);
- оставлены только нужные запросу колонки;
- нормализация строк: `trim()` у `brand` и `type`;
- исключены пары деталь–поставщик, где поставщик с жалобами (`comment LIKE '%Customer%Complaints%'`): убрано 320 строк (800 000 → 799 680).

Проверки качества (`sql/02b_quality.sql`): дубликатов пар `(partkey, suppkey)` — 0, строк с NULL в `brand`, `type`, `size` — 0.

|---|---|---|---|---|---|---|---|
| `silver.part_supplier` | `partkey`, `brand`, `type`, `size`, `suppkey` | 799 680 | 3,4 | PARQUET | ZSTD (по умолчанию) | нет | Колоночный формат подходит для аналитики. ## 5. Тесты производительности

### Методика

- Тестовая таблица: `partsupp` (самая большая, 800 000 строк). Для каждого варианта формат/кодек создана отдельная копия в схеме `bronze` командой `CREATE TABLE ... AS SELECT * FROM tpch.sf1.partsupp` (скрипт `bench/bench.py`, Python + клиент `trino`).
- Кодек задавался сессионным свойством `lakekeeper.compression_codec`, формат — параметром `format` в `WITH`.
- Размер: сумма `file_size_in_bytes` из `"таблица$files"`.
- Время записи: время выполнения `CREATE TABLE AS` (один замер).
- Время запроса: агрегация `SELECT suppkey, count(*) FROM <таблица> GROUP BY suppkey`. Запрос выполнялся 6 раз, первый прогон отброшен как прогрев, в таблице медиана остальных пяти.
- Условия не менялись: одни и те же ресурсы Docker, один масштаб `sf1`.

### Результаты

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | 0,057 с | 24,78 | Лучшее сжатие (в 4,3 раза меньше, чем без сжатия), но запись самая медленная: 2,91 с. Выигрыш в размере относительно ZSTD всего около 11%, а запись медленнее более чем вдвое. Подходит для данных, которые пишутся один раз и хранятся долго. |
| ZSTD | 0,058 с | 27,85 | Сжатие близко к GZIP (в 3,8 раза), а запись в 2,2 раза быстрее (1,30 с). Лучший баланс размера и скорости записи, поэтому ZSTD оставлен в слоях Bronze, Silver и Gold. |

Все варианты (`bench/results.csv`):

| Формат | Кодек | Размер, МБ | Сжатие к NONE | Запись, с | Запрос (медиана), с |
|---|---|---|---|---|---|
| Parquet | NONE | 106,89 | 1,00× | 1,03 | 0,058 |
| Parquet | SNAPPY | 39,02 | 2,74× | 0,92 | 0,050 |
| Parquet | ZSTD | 27,85 | 3,84× | 1,30 | 0,058 |
| Parquet | GZIP | 24,78 | 4,31× | 2,91 | 0,057 |
| ORC | ZSTD | 26,71 | 4,00× | 1,10 | 0,057 |

![Результаты бенчмарка](docs/screens/08-bench.png)

### Анализ

1. **Размер.** Без сжатия таблица занимает 107 МБ, с GZIP — 24,8 МБ. Основную массу даёт текстовая колонка `comment`: естественный текст сильно избыточен (низкая энтропия на символ), поэтому хорошо сжимается.
2. **Компромисс «сжатие — скорость».** GZIP сжимает сильнее всех, но медленнее всех пишет. SNAPPY пишет быстрее всех, но файл примерно на 40% больше, чем у ZSTD. ZSTD даёт сжатие, близкое к GZIP, при скорости записи, близкой к SNAPPY.
3. **Связь с теорией информации.** Степень сжатия определяется избыточностью данных. GZIP (Deflate) сочетает поиск повторов (LZ77) с кодированием Хаффмана, то есть использует энтропийное кодирование. SNAPPY использует только LZ-часть, поэтому быстрее, но дальше от предела сжатия. ZSTD сочетает LZ-подход с эффективным энтропийным кодированием. Кроме того, Parquet и ORC перед кодеком применяют собственные приёмы (колоночное хранение, словарное кодирование, RLE), поэтому разница между форматами с одинаковым кодеком невелика.
4. **Parquet и ORC.** ORC+ZSTD оказался на ~4% меньше Parquet+ZSTD (26,71 против 27,85 МБ) при близких временах. Разница небольшая и на других данных может измениться.
5. **Время запроса.** Различия между вариантами (0,050–0,058 с) лежат в пределах шума измерений: на 800 000 строк запрос слишком короткий. Вывод: на масштабе `sf1` влияние кодека на скорость чтения не обнаружено. Время записи измерялось по одному разу, поэтому различия порядка 0,1–0,3 с (например, NONE и SNAPPY) тоже нельзя считать значимыми. Уверенно различаются только размеры и более медленная запись GZIP.

### Ограничения

Один узел и небольшой объём данных, один замер времени записи, шум замеров сопоставим с разницей во времени чтения. На большем масштабе (`sf10`) разница в скорости чтения, вероятно, стала бы заметнее, но такой прогон не выполнялся.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Объёмы данных растут быстрее, чем способна масштабироваться одна обычная БД, а хранить всё в классическом хранилище дорого. Lakehouse хранит данные дёшево на объектном хранилище в открытых колоночных форматах (Parquet), отделяет хранение от вычислений и при этом добавляет поверх файлов то, чего не хватало «озеру»: транзакции, версии таблиц (снапшоты), эволюцию схемы. Один и тот же набор данных доступен разным движкам: в этой работе одни таблицы читали и Trino, и StarRocks без копирования. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Команды ниже. В таблицу `silver.part_supplier` добавлена колонка `loaded_at`, затем переименована в `etl_loaded_at`. У всех уже существующих строк в новой колонке `NULL`, данные не потерялись. Файлы с данными перезаписывать не пришлось: изменились только метаданные таблицы (в обычной БД на больших таблицах такая операция может быть долгой). |
| Пример скрипта восстановления данных из снапшота (time travel) | Скрипт `sql/06_timetravel.sql` приведён ниже. |

Schema evolution:

```sql
ALTER TABLE lakekeeper.silver.part_supplier ADD COLUMN loaded_at timestamp(6);
ALTER TABLE lakekeeper.silver.part_supplier RENAME COLUMN loaded_at TO etl_loaded_at;
SELECT * FROM lakekeeper.silver.part_supplier LIMIT 3;
```

![Schema evolution](docs/screens/09-schema-evolution.png)

Time travel (восстановление после «случайного» удаления):

```sql
-- 1. История версий таблицы
SELECT snapshot_id, committed_at, operation
FROM lakekeeper.silver."part_supplier$snapshots" ORDER BY committed_at;

-- 2. «Авария»: удалили часть данных
SELECT count(*) FROM lakekeeper.silver.part_supplier;               -- до: 799680
DELETE FROM lakekeeper.silver.part_supplier WHERE size = 3;
SELECT count(*) FROM lakekeeper.silver.part_supplier;               -- после: ⚠️ ЗАПОЛНИ

-- 3. Чтение старой версии без изменения таблицы
SELECT count(*) FROM lakekeeper.silver.part_supplier
FOR VERSION AS OF <snapshot_id_до_удаления>;

-- 4. Восстановление
CALL lakekeeper.system.rollback_to_snapshot('silver', 'part_supplier', <snapshot_id_до_удаления>);
SELECT count(*) FROM lakekeeper.silver.part_supplier;               -- после отката: ⚠️ ЗАПОЛНИ (ожидается 799680)
```

**⚠️ ЗАПОЛНИ:** подставь свои числа (после `DELETE`, после отката) и реальный `snapshot_id`, а также вставь скриншоты.

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| StarRocks (движок) | Уже входит в стек примера, поэтому не нужно ставить и настраивать отдельную систему. Читает Iceberg-таблицы напрямую через каталог Lakekeeper (внешний каталог Iceberg REST), то есть работает с теми же файлами, что и Trino, без копирования данных. Рассчитан на быстрые аналитические запросы, что подходит для агрегаций над Bronze. Для задачи «прочитать и проверить слой» BI-инструмент избыточен: нужен движок, который выполняет SQL по таблицам lakehouse. |

Скрипты развёртывания и действия (`sql/07_starrocks.sql`). StarRocks описан в том же `docker-compose.yaml` (`infra/`), образ `starrocks/allin1-ubuntu:4.0.1`, порты 9030 (MySQL-протокол) и 8030.

```bash
cd lakekeeper/examples/minimal
docker compose pull starrocks
docker compose up -d starrocks
docker compose exec starrocks mysql -P 9030 -h 127.0.0.1 -u root
```

  "iceberg.catalog.warehouse" = "demo",

## 7. Выводы

Медальон-архитектура разделяет сырые данные (Bronze), очищенные и связанные (Silver) и готовую витрину (Gold): на каждом слое можно проверять качество, а любой следующий слой пересобирается из предыдущего. Проверка Gold против исходного запроса подтверждает, что преобразования не исказили результат. Выбор формата и кодека определяется избыточностью данных: на `sf1` Parquet с ZSTD сжал самую большую таблицу примерно в 3,8 раза и пишется почти так же быстро, как с SNAPPY, поэтому он лучше GZIP (медленная запись при небольшом выигрыше в размере) и SNAPPY (заметно больший размер). На объёме `sf1` кодек не повлиял на скорость запроса, значимо различались размер и время записи. Открытый каталог Iceberg позволил читать одни и те же таблицы из Trino и StarRocks, а снапшоты дали возможность откатить данные после ошибочного удаления.
